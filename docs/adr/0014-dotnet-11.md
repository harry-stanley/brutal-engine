# ADR-0014: Target .NET 11

- **Status:** Accepted
- **Date:** 2026-11-26
- **Deciders:** the maintainer
- **Supersedes:** [ADR-0001](0001-dotnet-10-lts.md)

## Context

[ADR-0001](0001-dotnet-10-lts.md) chose .NET 10 LTS for two reasons: .NET 11 (STS) would have a shorter support window, and BRUTAL targets .NET 10. The [tech stack](../02-tech-stack.md#rejected-alternatives-summary) rejected .NET 11 for the same reasons. Checked again on 2026-11-26:

- **The support window is the same.** The release metadata (`https://dotnetcli.blob.core.windows.net/dotnet/release-metadata/11.0/releases.json`, and `10.0/releases.json` and `releases-index.json` next to it) lists .NET 11.0.0 as released on 2026-11-10 with SDK 11.0.100, release type `sts` and an `eol-date` of **2028-11-14**. .NET 10 (`lts`, latest 10.0.15, SDK 10.0.404) has the same `eol-date`, 2028-11-14. So .NET 11 isn't supported for less time than .NET 10; both end on the same day.
- **The language is C# 15.** The same file lists C# 15.0 for the 11.0.0 SDK. The engine builds with `LangVersion` `latest`, so it gets C# 15. Adopting new C# or library features isn't part of this change.
- **BRUTAL's `net10.0` libraries work under `net11.0`.** Every `Ahwoo.Brutal.*` package the engine uses ships only `lib/net10.0` (checked in the local NuGet cache: `Sdl`, `Vulkan` and `Vulkan.Abstractions` 2026.10.3, and their closure, such as `Core` 2026.10.4, `Logging` 2026.10.3, `Strings`, `Memory` and `Collections` 2026.10.2). NuGet gives a `net11.0` project the nearest compatible framework's assets, so restore picks those `net10.0` libraries unchanged. On the change that adopted this ADR, on the reference machine (Windows 11, RTX 2070 SUPER), the HelloWindow sample and the AOT smoke harness built on SDK 11.0.100 for `net11.0` and ran under JIT and as NativeAOT `win-x64` executables against them. BRUTAL itself is built and tested on .NET 10, so the engine now runs BRUTAL on a runtime BRUTAL doesn't test.
- **ADR-0011's pin is the .NET 11 line.** `Microsoft.Extensions.ObjectPool` 11.0.0, the version [ADR-0011](0011-brutal-objectpool-dependency.md) pins, belongs to .NET 11. Under `net11.0`, restore gives the engine's apps its `lib/net11.0` build, where a `net10.0` app got `netstandard2.0` (HelloWindow's `obj/project.assets.json`, which resolves the `11.0.0-preview.5.26302.115` package until the pin lands).
- **What the retarget changes in the build** (the regenerated `packages.lock.json` files):
  - The NativeAOT toolchain moves with the SDK: `Microsoft.DotNet.ILCompiler`, its `runtime.<rid>.Microsoft.DotNet.ILCompiler` packs and `Microsoft.NET.ILLink.Tasks` go from 10.0.15 to 11.0.0. No version in `Directory.Packages.props` changes.
  - .NET 11's shared framework (`Microsoft.NETCore.App` 11.0.0) contains `Microsoft.Extensions.Configuration.Abstractions`, `DependencyInjection.Abstractions`, `Logging.Abstractions`, `Options` and `Primitives`. NuGet prunes the 10.0.0 packages of those that BRUTAL's logging stack brought, and the framework's copies are used instead.
  - `Thread.Join` allocates on .NET 11.0.0 (32 bytes per call even on a thread that has already exited, 256 bytes when it blocks; nothing on 10.0.15; scratch probe on Windows x64). The two allocation-measurement guards (`AllocationMeasurementTests` in `BrutalEngine.Core.Tests` and `HelloWindow.Tests`) closed their measured window after a `Join`, so they now close it before joining.
  - The background-collection accounting problem that the [testing strategy](../05-testing-strategy.md) describes is still there on 11.0.0: with background collection turned on, the guard measured 8176 bytes on a thread that allocated nothing. Test projects that measure allocations keep background collection off.
- **Public maths types.** The [world design](../design/world.md) already takes `Vector2` and `Matrix3x2` from the BCL's `System.Numerics`, so World has no maths package dependency (docs/design/world.md:13).

## Options considered

1. **Stay on .NET 10 LTS** ([ADR-0001](0001-dotnet-10-lts.md)). Pros: exactly BRUTAL's tested runtime. Cons: no longer support than .NET 11 (both end on 2028-11-14); the engine runs on the older runtime for its whole M1-M2 development, and the ObjectPool pin stays a .NET 11 package in a .NET 10 product.
2. **Move to .NET 11 now.** Pros: the same end of support; the current runtime and compiler; ADR-0011's pin matches the runtime line. Cons: BRUTAL's packages are built for .NET 10, so a .NET 11-only BRUTAL problem is ours to find; games built on the engine need the .NET 11 SDK; STS releases get no extended support, so the move to the next LTS has to happen before 2028-11-14.
3. **Multi-target `net10.0` and `net11.0`.** Pros: games could stay on either. Cons: doubles the build, test and lock-file matrix, and every runtime difference (like `Thread.Join` above) needs handling twice.

## Decision

Decision (maintainer, 2026-11-26): option 2. The engine uses the .NET 11 SDK and runtime: every project targets `net11.0` (Roslyn components stay on `netstandard2.0`), and `global.json` pins SDK `11.0.100` with `rollForward: latestPatch`. Public maths types come from the BCL's `System.Numerics` (`Vector2`, `Matrix3x2` and so on), not from BRUTAL's Numerics.

## Consequences

- **Contributors and CI** need the .NET 11 SDK, 11.0.100 or a later `11.0.1xx` patch. CI reads the SDK from `global.json` (`actions/setup-dotnet` with `global-json-file`), so the workflows don't change. Dependabot's SDK rule still ignores major and minor updates, so it now proposes `11.0.x` updates only (`.github/dependabot.yml`).
- **Checked by tests:** the architecture tests' `TargetFrameworkTests` fail unless every engine assembly carries `TargetFrameworkAttribute` `.NETCoreApp,Version=v11.0`, the root `Directory.Build.props` sets `net11.0`, no other project or build file sets a framework (Roslyn components set `netstandard2.0`), and the test host runs on .NET 11.
- **BRUTAL on .NET 11:** HelloWindow and the AOT smoke harness exercise BRUTAL's SDL3 and Vulkan bindings on every CI run, under JIT and NativeAOT, on Windows and Linux. macOS stays best-effort and unverified ([ADR-0015](0015-tested-platforms-windows-linux.md)).
- **Public maths:** engine public APIs use `System.Numerics` types. `Ahwoo.Brutal.Numerics` and `.Maths` stay out of public signatures ([tech stack](../02-tech-stack.md#brutal-packages-used)).
- **Docs updated with this ADR:** [ADR-0001](0001-dotnet-10-lts.md) (status), [ADR-0011](0011-brutal-objectpool-dependency.md) (the errata link below, and two notes where it assumed .NET 10), the [ADR index](README.md), the [tech stack](../02-tech-stack.md), the [repository layout](../04-repo-layout.md), the [testing strategy](../05-testing-strategy.md), the [coding standards](../07-coding-standards.md), the [docs index](../README.md), the repository README, CONTRIBUTING.md and the bug report template. M0's records (the changelog's `0.1.0-alpha` entry, the spike results and the design notes' scratch compiles on SDK 10.0.404) stay as they were: they describe what ran on .NET 10.
- **Revisit when** .NET 12, the next LTS, ships (expected in November 2027, as ADR-0001 planned); the engine has to leave .NET 11 before its end of support on 2028-11-14. Also revisit if BRUTAL publishes packages that no longer load under the engine's target, or if a BRUTAL code path fails on .NET 11.

## Errata for ADR-0011

Accepted ADRs are only edited for status and links ([development workflow](../08-workflow.md#adr-process)), so these corrections to [ADR-0011](0011-brutal-objectpool-dependency.md) are recorded here:

1. **ADR-0011:21, the probe paragraph,** blends the JIT and NativeAOT results. The two runs showed different things:
   - **JIT** (Windows 11, .NET SDK 10.0.404, `net10.0`): the `Brutal.Strings` binding rented and returned a builder from `StringBuilderPool<char>.Shared`, and the loaded ObjectPool assembly reported informational version `11.0.0+297acf930fb0f5c07fd4e51d78e521b4ad2e5d1f`.
   - **NativeAOT** (`win-x64`): only the probe's `ObjectPool 11.0.0.0 / 11.0.0+297acf9, PROBE OK` line was seen. The `Brutal.Strings` pool calls weren't observed under NativeAOT.
2. **ADR-0011:45, the first "Revisit if" trigger,** is redundant and leaves out Windows. It should read: "the pinned 11.0.0 assembly fails any BRUTAL code path on any target".
3. **Follow-up evidence:** #82 (the ObjectPool 11.0.0 pin, an AOT probe and a package-closure architecture test) is the issue that proves the probe and the pin on Windows and Linux, under JIT and NativeAOT. It isn't done by this ADR's change.
