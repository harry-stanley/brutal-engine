# Changelog

All notable changes to BrutalEngine are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, versions are `0.y.z` and breaking changes can happen between minor releases. They are always listed under "Breaking", with migration notes. See [CI/CD and release: Versioning](docs/06-ci-cd-and-release.md#versioning).

Every pull request adds its user-visible changes to the `Unreleased` section.

## [Unreleased]

### Added

- `BrutalEngine.Graphics`, the render interface package, with a typed GPU handle per object kind: `BufferHandle`, `TextureHandle`, `TextureViewHandle`, `SamplerHandle`, `ShaderModuleHandle`, `SwapchainHandle`, `BindGroupLayoutHandle`, `PipelineLayoutHandle`, `BindGroupHandle`, `GraphicsPipelineHandle`, `ComputePipelineHandle`, and `DebugLabel` for interned pass and debug group names. Each is a non-owning value over a generational Core `Handle`; `default` is the null handle, and a handle of one kind never converts to another ([render interface design](docs/design/graphics.md#1-object-model-handles-ownership-and-destruction)).
- `BrutalEngine.Graphics.Vulkan`, the Vulkan backend package, with no public API yet. It starts with the backend's status mapping: every `VkResult` becomes an `ErrorKind` (out of memory, device lost as `Unavailable`, timeout, unsupported, invalid shader, otherwise `Native`), always with the code in `NativeCode`, and shader-module and pipeline creation failures become `InvalidData` ([Vulkan backend design](docs/design/graphics-vulkan.md#13-status-checking)).
- `BrutalEngine.Graphics`: `AdapterSelection`, which picks the GPU a device uses (`Auto`, or an override `ByIndex`, `ByName` or `ByType`), with `TryParse` and `ToString` for its text form (`auto`, `index:N`, `name:<text>`, `type:discrete`). Parsing is exact and case-sensitive, so numeric types, other casings, comma lists and surrounding whitespace are rejected. Also `AdapterType` and the `GraphicsFeatures` flags that devices negotiate ([render interface design](docs/design/graphics.md#2-device-creation-adapters-and-capabilities)).
- `BrutalEngine.Graphics.Vulkan`: the per-device call gate that every Vulkan result goes through. It marks the device lost on `VK_ERROR_DEVICE_LOST`, keeps it lost, and allocates nothing on success or failure. Also an internal fault injector, compiled into release builds and reachable only from the backend's tests, that makes the N-th call of a chosen Vulkan function return a chosen result once ([Vulkan backend design](docs/design/graphics-vulkan.md#12-device-loss)).
- `BrutalEngine.Graphics`: the adapter and capability descriptions a device reports: `GraphicsAdapterInfo` (index, name, type, driver, API version and the reasons an adapter was rejected), `GraphicsCapabilities` (the enabled `GraphicsFeatures` and the adapter's `GraphicsLimits`), and the `SampleCounts` and `FormatSupport` flags. Their `ToString` output uses the invariant culture ([render interface design](docs/design/graphics.md#2-device-creation-adapters-and-capabilities)).
- `BrutalEngine.Graphics`: the buffer and texture descriptions, `BufferDescription` (size, `BufferUsage` flags, `MemoryIntent` and a debug name) and `TextureDescription` (`TextureFormat`, size, array layers, mip levels, sample count, `TextureUsage` flags and a debug name; one layer, one mip level and one sample by default). Their `ToString` output uses the invariant culture ([render interface design](docs/design/graphics.md#5-resource-descriptions)).
- `BrutalEngine.Graphics`: the rules for buffer and texture descriptions, checked before the backend sees them. A non-positive size, side, layer or mip count, no usage, `TextureFormat.Undefined`, more mips than the full chain, a sample count other than 1, 2, 4, 8 or 16 (or above 1 with mips or layers), a `Readback` buffer with any usage but `CopyDestination`, or a value outside its enum throws `ArgumentException` or `ArgumentOutOfRangeException`. So does a side or layer count above the device's limits. Each exception names the field and the debug name. Device creation, which lands later, runs these checks ([render interface design](docs/design/graphics.md#5-resource-descriptions)).
- `BrutalEngine.Graphics`: the texture-view and sampler descriptions. `TextureViewDescription` has the texture, a `TextureViewDimension`, its mip and layer range (one of each by default) and a debug name. `SamplerDescription` has three `Filter`s, two `AddressMode`s, a `BorderColor`, `MaxAnisotropy`, an optional `CompareFunction` and a debug name, and defaults to nearest filtering, clamp to edge and no anisotropy. Also the `ShaderStages` flags for the pipeline and transition APIs. Their `ToString` output uses the invariant culture ([render interface design](docs/design/graphics.md#5-resource-descriptions)).
- `BrutalEngine.Platform.Sdl3`, the SDL 3 platform backend package, built on BRUTAL's SDL bindings. It starts with the backend's status checking: a failed SDL call becomes an `ErrorKind.Native` error naming the call and carrying SDL's error text, read only on failure, and the rules that map SDL video drivers to headless modes ([platform design](docs/design/platform.md#10-native-status-checks-and-the-brutal-log-bridge)).
- `BrutalEngine.Platform.Sdl3`: `SdlPlatformOptions`, the SDL-specific settings (`VulkanLibraryPath`, the Vulkan loader SDL loads, fully qualified), and the validation of `PlatformOptions` and `SdlPlatformOptions` that runs before SDL starts: each broken rule throws, naming the option ([platform design](docs/design/platform.md#11-what-platformsdl3-exposes)).
- `BrutalEngine.Platform.Sdl3`: starting SDL video, one session per process. The headless mode picks SDL's `offscreen` or `dummy` driver, the driver in use is reported along with the headless mode it gives, and a requested headless mode that an `SDL_VIDEO_DRIVER` environment variable overrides fails with `ErrorKind.Unsupported`. On macOS, starting the `cocoa` driver off the process's main thread fails instead of aborting (unverified on macOS) ([platform design](docs/design/platform.md#3-headless-mode)).
- `BrutalEngine.Graphics.Vulkan`: the internal loader setup that decides which Vulkan loader BRUTAL binds. Windows and Linux use the system loader and leave the drivers alone; an explicit loader is preloaded by absolute path on any OS; on macOS (unverified) the bundled loader is preloaded and `VK_DRIVER_FILES` is pointed at the bundled MoltenVK manifest unless `VK_DRIVER_FILES` or `VK_ICD_FILENAMES` is already set. A preloaded loader that BRUTAL didn't bind fails as `Unavailable` instead of falling back, and a missing loader is a `Result` failure rather than an exception ([Vulkan backend design](docs/design/graphics-vulkan.md#2-loader-setup)).
- `BrutalEngine.Graphics`: the rules for texture-view and sampler descriptions, checked before the backend sees them:
  - A view outside its texture, or a `Texture2D` view of several layers, throws `ArgumentOutOfRangeException` or `ArgumentException`. So does a view dimension outside `TextureViewDimension` (`ArgumentOutOfRangeException`).
  - A sampler value outside its enum, or a `MaxAnisotropy` that isn't positive, throws `ArgumentOutOfRangeException`.
  - Anisotropy above 1 needs the `SamplerAnisotropy` feature (`InvalidOperationException`) and must stay within the device's limit ([render interface design](docs/design/graphics.md#5-resource-descriptions)).
- `BrutalEngine.Platform.Sdl3`: the internal Vulkan surface source of an SDL window, which Graphics uses through `IVulkanSurfaceSource` once windows land. SDL's required instance extensions are copied once, as UTF-8 without NUL terminators, and read on any thread without allocating. `CreateVulkanSurface` makes the `VkSurfaceKHR` through SDL's status-returning call on the main thread; an SDL failure is `ErrorKind.Native` with SDL's text, and misuse (an index out of range, a zero instance, the wrong thread, a disposed window) throws ([platform design](docs/design/platform.md#4-vulkan-surface-source)).
- `BrutalEngine.Platform.Sdl3`: the internal rule for headless Vulkan windows: on SDL's `offscreen` driver, a window whose required extensions lack `VK_EXT_headless_surface` (no installed driver offers it, as on Windows) can't present, so window creation will reject it with `ErrorKind.Unsupported` and a message that says to run windowed ([platform design](docs/design/platform.md#3-headless-mode)).
- `BrutalEngine.Graphics.Vulkan`: `VulkanBackend.Create(VulkanBackendOptions)`, the backend's public entry point. It settles the Vulkan loader for the process in one call, logs the decision once in the `Graphics.Vulkan` category, and returns an immutable backend with nothing to dispose; its `LoaderPath` (the preloaded loader, or `null` for the system loader) is what the host passes to the platform. A missing loader, one that can't be loaded, or a different loader than BRUTAL already bound is an `ErrorKind.Unavailable` result; a null logger, a relative path or a `ValidationAllowance` without a reason throws `ArgumentException`. Creating it again with the same choice succeeds ([Vulkan backend design](docs/design/graphics-vulkan.md#the-backends-public-surface)).
- `BrutalEngine.Graphics`: the copy and upload types. `TextureRegion` (a rectangle of texels) and `TextureLocation` (a texture, mip level, array layer and `TextureAspect`, color by default) say where a copy or write goes; `TextureWrite`, `BufferCopy`, `TextureBufferCopy` (row pitch a multiple of `TextureBufferCopy.RowPitchAlignment`, 256 bytes) and `TextureCopy` describe the writes and copies; the `TransientUsage` flags say what per-frame transient memory is bound as. Their `ToString` output uses the invariant culture. The copy rules and the device methods that take these types land later ([render interface design](docs/design/graphics.md#6-uploads-transient-data-and-readback)).
- `BrutalEngine.Graphics`: the rules for buffer copies, buffer writes and transient allocations, checked before a copy is recorded or data is written. A `BufferCopy` needs `CopySource` and `CopyDestination` usages, a positive size, offsets and size that are multiples of 4, both ranges inside their buffers and, within one buffer, ranges that don't overlap. A buffer write needs `CopyDestination`, non-empty data and a range inside the buffer, with no alignment. A transient allocation needs a positive size and at least one `TransientUsage` flag, all of them defined. Violations throw `ArgumentException`, or `ArgumentOutOfRangeException` for ranges; huge offsets are rejected instead of wrapping. The device methods that run these checks land later ([render interface design](docs/design/graphics.md#6-uploads-transient-data-and-readback)).
- `BrutalEngine.Platform.Sdl3`: the internal size model and option rules that window creation will use. Content sizes convert to SDL window coordinates (content × display scale / pixel density) and pixel sizes back to content units (pixels / display scale), each side rounded to the nearest whole number with midpoints away from zero, matching SDL's high-DPI example for Windows and macOS. `WindowOptions` are checked before SDL is called: `null` options or title, a content-size side outside 1 to 16384, `ExclusiveFullscreen`, `default(DisplayId)` or a value outside its enum throws, naming the option and its value ([platform design](docs/design/platform.md#window-coordinates-pixels-and-content-units)).
- `BrutalEngine.Graphics`: the rules for copies between textures and buffers, in both directions. The texture needs `CopySource` or `CopyDestination` usage and one sample, and the buffer the other usage. The mip level, array layer and region must lie inside the texture, the region inside the mip level's size (`max(1, size >> mip)`), and the aspect must match the format. Depth can be copied to buffers but never from them. `BytesPerRow` must hold the region's rows and be a multiple of 256, `BufferOffset` a multiple of the texel size and of 4, and the buffer must hold every row. Violations throw `ArgumentException`, or `ArgumentOutOfRangeException` for ranges; huge offsets and row pitches are rejected instead of wrapping ([render interface design](docs/design/graphics.md#6-uploads-transient-data-and-readback)).
- `BrutalEngine.Graphics`: the rules for texture writes. The texture needs `CopyDestination` usage, a color format and one sample; the location and region must lie inside it; `BytesPerRow` is 0 for tight rows or at least the region's row size, with any pitch; and the data must hold at least `BytesPerRow * (Height - 1) + Width * texel size` bytes (longer data is allowed). Violations throw `ArgumentException`, or `ArgumentOutOfRangeException` for ranges ([render interface design](docs/design/graphics.md#6-uploads-transient-data-and-readback)).
- `BrutalEngine.Graphics`: the rules for texture-to-texture copies. The source needs `CopySource` usage and the destination `CopyDestination`; both need the same format and one sample; both locations and regions must lie inside their textures; and within one subresource the regions mustn't overlap. Depth textures can be copied this way. Violations throw `ArgumentException`, or `ArgumentOutOfRangeException` for ranges ([render interface design](docs/design/graphics.md#6-uploads-transient-data-and-readback)).
- `BrutalEngine.Graphics.Vulkan`: the internal instance creation that devices will use. It enumerates the loader's instance extensions and layers (with a bounded retry when a list grows between the two calls) and enables the window's surface extensions, portability enumeration when offered, the surface maintenance extensions when offered and the window's extensions include `VK_KHR_surface` (they depend on it), and `VK_EXT_debug_utils` when offered. With validation it also enables the Khronos validation layer, `VK_EXT_validation_features` from the layer's own list and synchronization validation; a missing layer, feature extension or `VK_EXT_debug_utils` is `ErrorKind.Unavailable` ("validation layer not installed"), never an unvalidated instance. Every enumeration and the creation return `Result`s, including BRUTAL's creation exception, and disposing the instance twice does nothing ([Vulkan backend design](docs/design/graphics-vulkan.md#1-instance-validation-and-the-debug-messenger)).
- `BrutalEngine.Platform.Sdl3`: internal SDL window creation, which the platform will expose through `IWindow`. A window is sized in content units: the estimate uses the target display's content scale, and the window is resized once if its own display scale and pixel density show the estimate was off. Its sizes, scale, density, state, mode, display, text-input and relative-mouse flags are a snapshot that the getters read without a native call or an allocation. A Vulkan window on the `NoSurface` headless mode fails with `ErrorKind.Unsupported` before calling SDL, a Vulkan window on `offscreen` without `VK_EXT_headless_surface` fails with `ErrorKind.Unsupported` and is destroyed, and a display that isn't connected fails with `ErrorKind.NotFound`. Every member checks the creating thread, then disposal ([platform design](docs/design/platform.md#windows-an-object-not-a-handle)).
- `BrutalEngine.Platform.Sdl3`: the internal SDL window's setters: `SetTitle`, `SetContentSize` (in content units, converted with the window's display scale and pixel density), `StartTextInput`, `StopTextInput` and `SetRelativeMouseMode`. Each returns a `Result`: a call SDL refuses (relative mouse mode on the `offscreen` driver) is `ErrorKind.Native` with SDL's message, not an exception. The new size shows in the snapshot once SDL has applied it and the window is refreshed (the event pump does so on the resize event); the text-input and relative-mouse flags change as soon as their setter succeeds. Each checks the creating thread, then disposal, then its argument, and a setter that succeeds allocates no managed memory ([platform design](docs/design/platform.md#windows-an-object-not-a-handle)).
- `BrutalEngine.Graphics`: the swapchain and frame-status types. `SwapchainOptions` asks for a `PresentMode` (`Fifo`, the default and the only mode every GPU supports, `FifoRelaxed`, `Mailbox` or `Immediate`), a `SwapchainFormat` (`Srgb` by default, or `Unorm`) and a debug name; `SwapchainInfo` reports a swapchain's size, format, present mode in use, image count and copy support; `SwapchainImage` is the image acquired for a frame. `AcquireStatus` (`Acquired`, `Recreated`, `Minimised`, `Skipped`, `SurfaceLost`, `DeviceLost`) and `FrameStatus` (`Ready`, `DeviceLost`) report acquisition and frame outcomes as values. Their `ToString` output uses the invariant culture. The device methods that use them land later ([render interface design](docs/design/graphics.md#3-swapchains)).
- `BrutalEngine.Graphics`: `WindowSurfaceSource` in `BrutalEngine.Graphics.Backend`, the form in which a window reaches a graphics backend, and the package's first reference to `BrutalEngine.Platform` (the one same-layer edge the layer map allows it). It forwards the window's required Vulkan instance extensions and surface creation to the window's `IVulkanSurfaceSource` unchanged, failures and exceptions included, and keeps the window's pixel size and whether it is minimised (the minimised flag or a zero side) as snapshots the device refreshes without a native call or an allocation. Only the device creates one, and that lands later ([render interface design](docs/design/graphics.md#3-swapchains)).

### Breaking

- The engine targets .NET 11 (`net11.0`) instead of .NET 10 ([ADR-0014](docs/adr/0014-dotnet-11.md), superseding ADR-0001). `global.json` pins SDK 11.0.100 (`rollForward: latestPatch`). Migration: games and tools that reference BrutalEngine projects or packages target `net11.0` and build with the .NET 11 SDK. BRUTAL's `net10.0` packages are used unchanged; NativeAOT builds use the 11.0.0 compiler packs.

### Added

- `BrutalEngine.Platform`, the backend-neutral platform abstraction (no backend yet): `IWindow` (sizes in window coordinates, pixels and content units, state, mode, display, text input and relative mouse mode, and setters that return `Result`), `IVulkanSurfaceSource` (the instance extensions a window needs and `CreateVulkanSurface`, using only `nint` and spans), and the value types `WindowId`, `WindowSize`, `DisplayId`, `WindowState`, `WindowMode` and `DisplayMode` ([platform design](docs/design/platform.md)).
- `BrutalEngine.Platform`: `PlatformOptions` (organisation and application names, headless mode, event and text capacities, clock, user data directory and logger) and `WindowOptions` (title, size in content units, mode, resizability, high pixel density, surface and display), the settings a host passes to a platform backend, with `WindowSurface` and `HeadlessMode`. The records document every default and valid range; the backend validates them when it creates the platform or window ([platform design](docs/design/platform.md#11-what-platformsdl3-exposes)). `DisplayInfo` and `DisplayRect` describe a connected display (its desktop bounds, usable bounds, content scale and current mode, formatted with the invariant culture), and `SystemCursor` names the OS cursor shapes. `MessageBoxRequest` and `MessageBoxKind` describe a modal message box and its icon.
- `BrutalEngine.Platform`: `Scancode` (`ushort`), the physical key, with SDL 3's names and values for every key: the USB HID keyboard/keypad usage ids from 4 to 231, and SDL's own values from 257 to 290 for the mode switch, media, application-control and phone keys. `Unknown` is 0; values without a member can still arrive, and members are only ever added ([platform design](docs/design/platform.md#keys)).
- `BrutalEngine.Platform`: the values that input events carry. `Keycode`, the key in the current layout in SDL 3's encoding (a Unicode code point, or the scancode with bit 30 set), with `IsCharacter`, `Character` and `FromScancode`. `KeyModifiers` (`ushort` flags with SDL's bits, plus `Shift`, `Control`, `Alt` and `Gui` for either side), `MouseButton` and the `MouseButtons` flags (both `byte`, with SDL's numbering). The payload records `KeyEventData`, `TextEventData`, `MouseMotionData`, `MouseButtonData` and `MouseWheelData`, each unmanaged and sized for its slot in the event's 24-byte payload; the mouse records format with the invariant culture ([platform design](docs/design/platform.md#keys)).
- `BrutalEngine.Platform`: `PlatformEventKind` (`ushort`), what a platform event reports: `None` (0), `QuitRequested`, the window kinds, `KeyDown`, `KeyUp`, `TextInput`, the mouse kinds and the display kinds, with values that are only ever appended, never renumbered. `PlatformEventHeader`, the kind, window and timestamp every event carries, formatted with the invariant culture ([platform design](docs/design/platform.md#the-event-struct)).
- `BrutalEngine.Platform`: `PlatformEvent`, a 40-byte unmanaged tagged union: the 16-byte header (`Kind`, `Window`, `Timestamp`, `Header`) and a 24-byte payload read through typed views (`Key`, `Text`, `MouseMotion`, `MouseButton`, `MouseWheel`, `Size`, `Display`, `Scale`) at the documented offsets. One factory per payload (`Create`, `CreateKey`, ... `CreateDisplayScale`) checks the header: a kind that isn't the factory's, a `Window*` kind with a default window, or `QuitRequested` or a `Display*` kind with a non-default one throws `ArgumentException`. Reading a view the kind doesn't carry throws `InvalidOperationException`. Payload values are stored as given. Creating and reading events allocates nothing ([platform design](docs/design/platform.md#the-event-struct)).
- `BrutalEngine.Platform`: `PlatformEvent.ToString` describes the event: its header, then the payload its kind carries, read through that kind's views, for example `PlatformEvent { Kind = WindowResized, Window = 3, Timestamp = 120, Size = WindowSize { Width = 800, Height = 600 } }`. It never throws, whatever the kind (`None` and values without a member print the header only) and the payload values, and formats with the invariant culture whatever the current culture is ([platform design](docs/design/platform.md#the-event-struct)).
- `BrutalEngine.Core`: `ThreadAffinity`, which captures an owner thread and checks that a call is on it (`ThrowIfNotCurrentThread` runs in every build, and is a null check plus one integer comparison that allocates nothing when it passes), and `WrongThreadException`, thrown with the member's name and both managed thread ids when the check fails.
- `BrutalEngine.World` (new package, the world model of ADR-0006): `WorldOptions`, validated when a world is created (chunk size, initial entity capacity and limit, component-type width, hierarchy depth, clock and name, each named in the exception), and the `EcsWorld` shell: construction, owner-thread checks that throw `WrongThreadException` naming the member, and idempotent disposal. The world never owns or disposes an allocator it is given. `Entity`: an 8-byte generational handle (index plus generation, `Entity.Null` as the default, a raw 64-bit value that round-trips and rejects non-canonical zero-generation values, and `Entity(12v3)` formatting).
- `BrutalEngine.World`: each world now keeps an entity table, allocated from the world's allocator and freed when the world is disposed. It has a 16-byte record per slot, reuses freed slots first in, first out with an advanced generation, retires a slot freed at the last generation instead of wrapping, grows by doubling up to `WorldOptions.MaxEntities`, and names that option when it runs out of slots. A world now reserves `WorldOptions.InitialEntityCapacity` slots from its allocator when it is created. No public API change.
- `BrutalEngine.World`: `EcsWorld.IsAlive` and `EcsWorld.IsPending` look up any entity without throwing for null, stale, retired or out-of-range values, and allocate nothing. A pending entity (reserved for a command buffer and not yet placed) is pending and not alive, and its slot counts towards `WorldOptions.MaxEntities`.
- `BrutalEngine.World`: `StableComponentId`, a component type's identity across processes and builds. `StableComponentId.FromFullName` is 64-bit FNV-1a over the UTF-8 bytes of the type's full metadata name (`MyGame.Outer+Inner` for a nested type), encodes a lone surrogate as U+FFFD, and allocates nothing. Its known vectors are pinned in tests ([world design](docs/design/world.md#3-components-and-the-registry)).
- `BrutalEngine.World`: the component value types. `IComponent` marks an unmanaged struct as a component and supplies its `ComponentInfo` through a static abstract `Info`, read without reflection (NativeAOT-safe). `ComponentInfo` holds the stable id, schema version, full metadata name and tag-ness; `ComponentId` is a registry's dense id, which only a registry can create with a chosen index; `ComponentType` describes a registered type (id, info, size and alignment). All compare by value ([world design](docs/design/world.md#3-components-and-the-registry)).
- `BrutalEngine.World`: `ComponentRegistry`, each world's component types, reached through `EcsWorld.Components`. `Register<T>()` is idempotent and hands out dense `ComponentId`s in registration order, taking size and alignment from the type itself; `TryGetId<T>` (one static load and one array read, through a process-wide ordinal per type held in a static `int`) and `TryGetId(StableComponentId)` look types up without allocating; `GetComponentType` describes a registered type and rejects an id past `Count`. Registering more than `WorldOptions.MaxComponentTypes` types throws, naming the option. Every member checks the world's owner thread and throws once the world is disposed ([world design](docs/design/world.md#3-components-and-the-registry)).
- `BrutalEngine.World`: component registration enforces the rules. `Register<T>()` throws `ArgumentException` for a type over 1,024 bytes or aligned to more than 64 bytes, or with an invalid `ComponentInfo` (schema version 0, a null or empty full name, a stable id that isn't `StableComponentId.FromFullName` of the name, or a tag whose size isn't 1), and `InvalidOperationException` when another registered type has its stable id: a hash collision, the same name with another schema version or tag-ness, or a different type with the same name. Each message names the type(s) and the limit or field, and a rejected registration leaves the registry unchanged ([world design](docs/design/world.md#3-components-and-the-registry)).
- `BrutalEngine.World`: the internal chunk layout that archetype storage will use: entity ids first, then one column per non-tag component aligned to at least 16 bytes, with the largest row count that fits the chunk. An archetype that fits fewer than 16 rows in a chunk, alignment padding included, is rejected with `InvalidOperationException` naming its components ([world design](docs/design/world.md#4-storage)).
- `BrutalEngine.World`: `EcsWorld.TrimMemory`, which returns the world's pooled empty chunks to the allocator. Each world now keeps a pool of chunk blocks (`WorldOptions.ChunkBytes` each, 64-byte aligned, from the world's allocator): emptied chunks go back to the pool rather than the allocator, so steady spawn and despawn churn makes no allocator calls, and the pool is freed when the world is disposed ([world design](docs/design/world.md#4-storage)).
- `BrutalEngine.World`: the internal chunk table that each archetype will keep: its chunks (a block from the world's chunk pool and a row count each) and, per chunk and column, a `Changed` and an `Added` tick, stored outside the chunks so a filtered query can skip a chunk without touching it. A new chunk's ticks start at the tick it was added at; the arrays grow by doubling, all or nothing, so a failed allocation leaves the table unchanged; an emptied last chunk goes back to the pool, and disposing the table returns every block. If the allocator throws while the pool frees its blocks (`EcsWorld.TrimMemory`), the blocks not yet freed stay pooled and a later trim frees them ([world design](docs/design/world.md#4-storage)).

### Changed

- `Microsoft.Extensions.ObjectPool`, which BRUTAL's `Ahwoo.Brutal.Strings` brings in as the pre-release `11.0.0-preview.5.26302.115`, is pinned centrally to the 11.0.0 GA release ([ADR-0011](docs/adr/0011-brutal-objectpool-dependency.md)), so `samples/HelloWindow` and its builds ship the GA package. The smoke harness checks at start that BRUTAL's string-builder pool runs on it, and an architecture test keeps `Ahwoo.Brutal.Strings` and the pool out of Core, Platform, Graphics and World.
- Package versions: builds after the `v0.1.0-alpha` tag are versioned `0.2.0-alpha.0.N` (N = commits since the tag) until `v0.2.0` is tagged, instead of `0.1.0-alpha.N`.
- CI builds, tests and smoke-runs on Windows and Linux only. macOS is best-effort and unverified ([ADR-0015](docs/adr/0015-tested-platforms-windows-linux.md)), so there is no `hello-window-osx-arm64` artifact any more. The macOS code, the `osx-arm64` RID, the pinned natives and the macOS setup action are kept.
- `samples/HelloWindow` logs through `BrutalEngine.Core`'s `Logger` and `ConsoleLogSink` (categories `HelloWindow` and `HelloWindow.Vulkan`) instead of plain console writes, so each line now reads `2026-11-26T01:02:03.456Z INFO [HelloWindow] message`. Messages may be up to 64 KiB, so a failure's full exception report stays whole. The validation messenger keeps its counts per instance and reaches them through the callback's user data, with no static state. CI's splash check matches the new line format.
- `samples/HelloWindow`'s published output, and so the `hello-window-<rid>` CI artifacts, no longer include XML doc files (`HelloWindow.xml`, `BrutalEngine.Core.xml`). CI checks there are none.

### Fixed

- `BrutalEngine.World`: a component registration that runs out of memory while the registry's tables grow leaves the registry unchanged, as documented. Before, `TryGetId(StableComponentId)` could still find the failed type's stable id and return an id that `GetComponentType` rejects.
- `BrutalEngine.World`: the exception for a registration that conflicts with a registered component of the same full name (another schema version, tag-ness or CLR type) names the new type's CLR type and assembly, so it says which of the two types is new.
- `BrutalEngine.Core` logging no longer allocates a new message buffer after a gen2 collection under high memory pressure. The buffers came from `ArrayPool<byte>.Shared`, whose trim then drops every thread's cached arrays; each logger now keeps up to 8 buffers of its own, falling back to the shared pool only when more threads log at once. A formatter that throws now returns its buffer instead of leaving it to the garbage collector ([logging design](docs/design/logging.md#memory-and-threading)).
- `Logger.SetLevel` no longer allocates after a garbage collection. It validated the level with `Enum.IsDefined`, which rebuilds a weakly held runtime cache (240 bytes) on its first call after any collection.
- `samples/HelloWindow`: `--require-driver MaxEnum` is rejected (it's Vulkan's sentinel value, not a driver), an unnamed `VkResult` appears once in error messages instead of twice, a failure inside an SDL callback is reported with its stack trace and the inner exception, and on the splash's 1:1 copy path the window's minimum size is recomputed when the pixel density changes (for example, after a move to another display).

- Community health files: contributing guide, security policy, code of conduct (Contributor Covenant 2.1), this changelog, pull request and issue templates, and CODEOWNERS.
- `samples/HelloWindow`: an SDL3 window presenting a Vulkan 1.3 clear-colour swapchain, with resize and minimise handling, validation counting and NativeAOT support.
- `BrutalEngine.Core.Logging`: an instance-owned logging facade (`Logger`, `LogCategory`, `ILogSink`) with a global minimum level and per-category overrides, UTF-8 formatting that allocates nothing for common types (enabled or not), messages truncated to a byte limit, and sink failures isolated and counted. It has no BRUTAL dependency.
- `samples/HelloWindow` on macOS uses the Vulkan loader and MoltenVK bundled next to the executable, so a published build runs with no Vulkan SDK, Homebrew or `VK_DRIVER_FILES`.
- CI runs HelloWindow with validation on Linux, Windows and macOS (JIT and NativeAOT, with negative tests) and uploads the NativeAOT build per platform. Any change under `samples/` gets the full CI tier.
- `BrutalEngine.Core.Logging.Sinks.ConsoleLogSink`: writes each log entry as one UTF-8 line (`2026-11-25T03:04:05.678Z INFO [Category] message`) to standard output, or to standard error from a configurable level (default `Warning`), flushing on errors. Streams can be injected, and steady-state writes allocate nothing.
- `BrutalEngine.Core.Logging.Sinks.MemoryLogSink`: keeps the most recent log entries in fixed, preallocated memory (by entry count and message bytes), overwriting the oldest and counting drops. `CopyTo` copies them into caller buffers, for crash reports and the debug overlay, without allocating.
- `BrutalEngine.Core.Logging.Sinks.RotatingFileLogSink`: writes log lines to `engine.log` in a directory the host provides. Each run starts a fresh file, files rotate by size (default 10 MiB), at most `MaxFiles` are kept (default 5), and entries at or above `FlushLevel` (default `Warning`) are flushed as soon as they're written. It's thread-safe and never throws on I/O failure: it faults permanently, reports the error in `Fault` and counts dropped entries in `DroppedCount`. Steady-state writes allocate nothing.
- `samples/HelloWindow` shows the official BRUTAL logo for at least 2.0 s (the first 120 frames when headless) before the scene, as BRUTAL's licence requires. The logo is drawn unaltered except for scaling, with no shaders: it is composited on the CPU and blitted, or copied at 1:1. A surface that can't show it is a setup failure, never a silent skip. The published output ships BRUTAL's `LICENSE.txt` and `NOTICE.txt`, each BRUTAL package's third-party licences in `LICENSES/`, and a generated `CREDITS.txt` with BRUTAL's and BrutalEngine's copyright lines. CI checks them, plus that the scene ran after the splash.
